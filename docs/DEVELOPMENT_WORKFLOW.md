# Порядок разработки и публикации SiteMath

Этот порядок нужен для сохранения стабильного сайта, уменьшения лишних запусков GitHub Actions и возможности восстановить любую рабочую версию. Он **не меняет** учебные задания и геометрию.

## Ветки

- `main` – проверенная версия сайта, которая публикуется через GitHub Pages. Не сохранять в неё серию промежуточных исправлений.
- `work/<тема>` – короткоживущая рабочая ветка от актуального `main`. Подготавливать и проверять здесь изменения по **одной уже поставленной задаче**. Ветка `work/next-batch` создана для следующего комплекта работ; после завершения и объединения её следует удалить и при необходимости создать новую от обновлённого `main`.
- Не менять ветку по умолчанию и не переписывать историю `main`.

## Один логический комплект изменений

1. Перед началом сверить `main`, исходные JSON, код решателя, тесты и документы. Не повторять уже сделанные исправления.
2. В рабочей ветке подготовить связанные изменения **всех затрагиваемых файлов**. Когда используется подключение GitHub, для групповой записи файлов предпочтительны Git tree → один commit → обновление ссылки ветки, а не отдельный коммит через Contents API для каждого файла.
3. Сохранять промежуточные результаты в той же рабочей ветке, если работа большая. Частые осмысленные коммиты в рабочей ветке допустимы и не нарушают безопасность. Не оставлять длительную работу без контрольной точки только ради уменьшения количества коммитов.
4. После подготовки комплекта проверять целостность JSON и сборку `variants.js`, геометрические инварианты, все затронутые варианты, затем общий runtime- и мобильный браузерный аудит. При ошибке исправлять рабочую ветку, а не `main`.
5. **После готовности комплекта** открыть Pull Request из рабочей ветки в `main`. Действующий workflow `.github/workflows/check.yml` запускает тесты для PR; новые коммиты в открытом PR повторно запускают проверки. Поэтому до PR желательно завершить основную пакетную работу.
6. Объединять PR лишь после успешных проверок. Для законченной задачи предпочтителен **Squash merge** с понятным описанием результата. После публикации проверить статус GitHub Pages и отсутствие ошибок. Следующую задачу начинать от актуального `main`.

## Защита от потерь и конфликтов

- Не использовать принудительную перезапись (`force push`) ветки `main`, а также не удалять из неё старые коммиты ради «красоты» истории.
- Перед обновлением рабочей ветки сверять фактический SHA её вершины. При наличии конкурирующих изменений не перезаписывать их; сначала получить свежую версию и согласовать изменения.
- Хранить оригинальные университетские рисунки и исходные данные отдельно от адаптированных учебных схем, как это уже сделано в проекте.
- Падение тестов не удаляет коммиты. Восстановление возможно через историю Git; незакоммиченные изменения, напротив, могут быть потеряны при сбое.
- Наличие рабочей ветки **не является защитой `main` от прямой записи**: правила защиты ветки на GitHub надо настраивать отдельно, если потребуется технический запрет. Данный регламент описывает безопасный порядок работы, а не гарантирует автоматическую блокировку ошибочного push.

## Текущие триггеры CI

В `.github/workflows/check.yml` сейчас включены `push` только для `main` и `pull_request`. Поэтому обычный коммит в ветку `work/*` сам по себе **не запускает** этот workflow; проверка в GitHub Actions начинается при открытии PR или его обновлении. Публикация GitHub Pages не должна запускаться от коммита только в рабочую ветку.
